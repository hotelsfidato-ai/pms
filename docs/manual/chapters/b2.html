Chapter B2

People and security

For the owner. The roles and who sees what, how a person signs in and on which devices, the three locks every request passes, how each hotel's data is kept apart, the record of who did what, and why the test sign-ins can never reach the live system.

B2.1The roles

Every person has a role at each hotel they work at. The list of roles is one list for the whole group, not one per hotel D22-24. A person can hold different roles at two hotels, for example GM at one and Reception at another; the screens and the server both use the role at the hotel in the address D26-13. A group administrator is the owner at every hotel.

Why it works this way

  • A shorter menu, nothing lost (the owner, 15 September): a new receptionist faced 47 menu entries and asked what to do. Their own work is in their menu; the rest is one search away.
  • One matrix, read by the screens and the server (Figure B2-01). Until 22 September it lived only in the website, and the server let any rostered person write anything at their hotel; the owner had it fixed before the first real day D21-88. Since then a menu and the server cannot disagree.
  • A control the server would refuse is hidden, not left as a button that fails D24-18 D24-27. And a screen the role cannot open names its menu entry: “You are signed in as Reception, which does not include Guest 360.” D27-5
  • Nobody runs somebody above them: a GM cannot change, switch off or reset the password of the hotel's Admin or the owner, and nobody can switch off or change their own access D24-19 D24-28.

B2.3Three locks on every request

  • Sign-in is Firebase's: it gives the browser a pass, and the API checks the pass on every request. Firebase knows nothing about roles or hotels.
  • The role gate is the API's. Every write, and since 28 September every read, finds its rule and asks the person's role at the hotel in the address. A route with no rule is refused for everybody, and a test lists every route the server has and fails on one without a rule.
  • Row security is the database's. Every table that belongs to a hotel carries the hotel, and the database itself shows a person only the rows of hotels they work at (B2.4).

Three doors have no person behind them and do not use the role gate: the guest's page (its link is the credential, B2.7), an outside till (its outlet key, B5.7) and SU (its own key, B5.6). Each of them still works inside row security, as an account at one hotel.

B2.4Each hotel's data kept apart

  • Every hotel's table carries the hotel, and the database applies the rule to every question asked of it, by anyone. The API connects as an account (pms_app) that can read and write rows and nothing else; it cannot switch the rule off. So a forgotten filter in the code still returns only the asker's hotels.
  • Guests are kept once for the whole group, on purpose: one person across seven hotels keeps their history, and a blacklist cannot be walked round by booking elsewhere. Their name and phone are shared. Their ID documents are not: they live in a table of their own, readable only at a hotel that holds a booking for that guest (migration 013), and only by the roles that check guests in D25-38.
  • Machines are scoped like people. An outside till, SU and the CRS reader each work as a service account at one hotel, so a misconfigured till cannot even see another hotel's guests. The CRS reader works as a Viewer at its one hotel, with no sign-in D27-286 (4).
  • When the system is sold, each customer gets its own database on the shared server D27-278, so no customer's rows ever sit beside another's.

Watch out

  • Customers' databases share one login (pms_app), by the owner's choice, with a check at start-up that the database belongs to the customer the API is set for D27-279 (1). The owner chose this knowing that a break-in at one customer's API could reach every customer's data (deploy/README.md, Add a customer).
  • A test of who sees what must run as pms_app: the database's superuser skips row security entirely and would pass any check. The isolation tests run as pms_app for that reason (MEMORY 47).

Why it works this way

One database, one set of tables, the hotel on every row and the rule in the database was chosen at the start over a database or a set of tables per hotel: those make the group's own reports hard and multiply every change by seven (docs/MASTER-ARCHITECTURE.md § 5). Adding a hotel is then a matter of data, never of building anything. One gap was found by use rather than by a test: the list of hotels itself was not scoped, so any member of staff could list every property and its GSTIN. It was closed, and no guest data or money had crossed between hotels (MEMORY 59).

B2.5Signing in, passwords and devices

  • An email and a password, kept by Firebase. The GM (or an Admin) adds the person on People, types their first password and tells them; nothing is emailed (src/modules/admin/MODULE.md). A forgotten password is reset by the GM on People (A0.1).
  • At least 10 characters for the owner, an Admin and a GM, 8 for everybody else D27-243. Somebody given one of those three roles while their password is shorter sets a longer one at their next sign-in D27-245.
  • Every sign-in is kept 90 days: when, and on what device. The owner sees everybody's; an Admin sees the people at their own hotel D27-245.
  • Sign out this device: the owner or an Admin can make the server refuse one device's sign-in from its next request D27-255.
  • Switching a person off on People also switches off their Firebase sign-in; switching them back on turns it back on D27-275 (4). A GM removes a person who also works at another hotel from their own hotel only; only the group administrator switches them off everywhere D23-4.

Why it works this way

  • No "sign out everywhere" and no "block a device": switching the person off already does both D27-255.
  • Adding somebody can never take over an existing account. From 9 to 15 September a GM could "add" the owner's email with a password of their choosing, and the sign-in service changed the owner's password before the database refused; the GM could then sign in as the owner. Closed on 15 September (migration 088): the address is checked before the sign-in service is touched. The lesson kept: something that cannot be undone happens after every check, never between them (MEMORY 263).

B2.7The guest's own doors

  • The guest's link is the only credential their page has. The server keeps only a fingerprint of it, and it stops working at 11:00 the morning after check-out (src/modules/guest-messaging/MODULE.md).
  • Before a code, the page shows only what a clerk would say across a counter, never the bill. The code goes to the booking's own phone or email, or the guest uses Google with the booking's email D18-13 D27-207. A phone that answered it stays unlocked for a day D27-169; a forwarded link asks again D21-6.
  • The QR card in a room shows the hotel and the room number only D21-14; reprinting a card stops the old one at once D21-16.
  • ID photos are encrypted with the hotel's own password and kept in Google Drive; the server keeps none D27-208 D27-209. Online, an Aadhaar photo must be masked D27-207. Once confirmed, a kept photo is seen only by the owner, Admin and GM, every view is recorded, and only they delete one, with a reason D27-210.
  • A typed Aadhaar number is accepted in full D21-17; screens show its last four digits and only the printed registration card shows it all D21-18. Whether the hotel may keep the full number is with the lawyer D25-37.

B2.8The test sign-ins never reach the live system

On the development computer the sign-in page has buttons that sign in as a test owner, GM or receptionist with no password. They exist for testing only (the owner, 14 September: "keep it simple for the local system; for production remove it"). Three separate locks keep them off the live system:

  1. The build refuses. Building the website for release fails if any trace of the test sign-ins is in the result.
  2. The live API refuses to start if the test sign-in is switched on with the production setting. It does not warn; it stops.
  3. The tests cannot reach the live sign-in service. The test runs blank the Firebase key, and a test fails if it ever comes back. On 15 September a proof run reached the live sign-in service and created two junk accounts before this lock existed (MEMORY 264).

The developers' Console, which can create properties and people, exists only in development builds.

Watch out

  • The server's secrets live only in its settings file: the Firebase Admin key, the sending workflow's secret, the CRS login, the ID photo passwords. Never in the code, a screen, a chat or this book. The Firebase Admin key passed through a chat once and is on the owner's list to replace (HANDOVER.md § 8).
  • n8n's encryption key is a master password for every login n8n holds: never pasted anywhere (HANDOVER.md § 5). n8n is open to the internet behind its own sign-in, so two-step sign-in there matters D21-96.
  • The two spare database logins (for migrations and read-only use) could still sign in on 4 October; they lose their sign-in with migration 202, in the next release D27-279 (4).

Left out, and why

  • Two-step sign-in for the owner, Admins and GMs: after this release, once the owner upgrades Firebase D27-243.
  • Roles per hotel: one list for the group D22-24.
  • A person's own "my devices": later D27-255.
  • The address a sign-in came from is kept, not shown D27-243.
