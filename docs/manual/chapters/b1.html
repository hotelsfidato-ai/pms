Chapter B1

The system at a glance

For the owner. What runs where, what talks to what and why it was built that way, one booking's journey through all of it, what watches it, and the risks that come with the shape it has. The rest of Part B goes into each part.

B1.1The parts, in one picture

Fidato PMS is three things you own and run, and a handful of outside services it talks to. Staff use it in a web browser; nothing is installed on their computers. The website is only the screens. Every figure, every rule and every check lives on one server, in the API and the database behind it.

Why it works this way

  • The PMS is the record for rooms, availability, prices and bookings; the CRS and the other apps show copies D17-28. One record means one answer to "is the room free?".
  • A real database, not Firestore. Chosen at the start (docs/MASTER-ARCHITECTURE.md, 26 August): a hotel's day needs changes that succeed or fail together (a check-in touches the room, the booking and the bill), and sums over thousands of rows. Firestore, which the CRS uses, can do neither well and charges for every row a report reads.
  • Sign-in kept apart from permission. Firebase only says who you are; your role and your hotels live in the database, where the rules are. Roles never live in Firebase, so nothing kept there can make anybody an owner.
  • The website apart from the API. Several clients talk to the same API (the screens, the guest's page, outside tills, SU), so the API is the contract. The website needs no server of its own and is the same for every hotel.
  • n8n on the PMS's server, holding the words D17-29 D17-87: a message's wording, the mailbox and the WhatsApp login are changed in n8n, without a new release. The PMS sends the figures and the exact A4 PDF the desk prints D17-91 D18-20. Since 30 September every guest message goes through one workflow D27-98 D27-186.
  • Separate apps, joined by bridges, for good: the CRS stays the sales team's app and the leads app stays separate; the PMS reads them D27-27 D27-276 (7). That replaced the plan of 15 September for one combined system.
  • One server, for now D27-276 (1): the backups must reach storage off the server and a full restore is rehearsed monthly; a standby server comes once five or more hotels pay.
  • What the server records about itself stays on it: each request's time and result, errors and slow queries, kept 180 days, shown on System health; no guest data leaves India for it D27-91 D27-92.
  • When it is sold, each customer gets its own database on one shared server D27-278: there is never a "which customer" column, so one customer's rows cannot show up in another's screens D21-12.

Said differently in the documents

The documents call the n8n that sends guest messages "the CRS's n8n", because the CRS's own voucher workflow and its mailbox and WhatsApp logins live there (deploy/n8n/IMPORT.md). The release steps of 5 October open that workflow at n8n.fidatohotels.com, the n8n on this server (docs/go-live/RELEASE-5OCT.md, step A9). This book takes them to be the same n8n; no single document says so in one sentence.

Two other ways a booking arrives

  • From the CRS. A salesperson books one of the group's own hotels in the CRS. Every five minutes the PMS reads the CRS's new bookings with a read-only login of its own, and each becomes a booking Waiting for the hotel, its room held. The hotel confirms it; then the one voucher goes D27-35 D27-171. Details in B5.5.
  • From a booking site, through SU. SU will push each booking to the API's own door the moment the site takes it D17-79; a booking for a room no longer free is not made, and SU is told at once D17-80. Built, not connected yet (B5.6).

Why it works this way

  • The message follows the booking, it is not part of it. A job sends it within a minute, outside the booking itself, so a slow or broken WhatsApp can never stop a clerk saving a booking. The cost: the voucher leaves up to a minute after Save, not the instant it is pressed (src/modules/guest-messaging/MODULE.md).
  • One door for every booking. The desk, the CRS and the booking sites all end at the same place on the server, so every rule (the room held, the reference, the voucher) applies to all of them, including a way in added next year.
  • The business date, not the clock, dates every line (B3.2): a bill settled at 00:40 belongs to the day the hotel has not yet closed.

B1.6The risks that come with this shape

Watch out

  • One server holds everything: the API, the database, n8n and the backups. If it is lost, everything stops until it is rebuilt. There is no standby yet D27-276 (1).
  • The backups are on that same server. Copies off it, to Oracle Object Storage in Fidato's own account, were chosen D27-18 D27-19, then put on hold D27-285 (5). A read-only check of the live server on 4 October found the upload setting empty: every night's backup says "this copy is on this disk only" (MEMORY 385). Until the copies go off the server, losing the server loses the backups with it.
  • The Oracle account stays on its free tier D27-285 (4). Oracle may take back a free server that looks idle; the owner chose this knowing it.
  • n8n watches the box it runs on. If the server goes down, n8n cannot say so; UptimeRobot is the outside backstop D27-20. Whether it has been set up is not recorded in the documents. And the same check of 4 October found the backup's alert address empty too, so a failed backup on live tells nobody until it is filled in (MEMORY 385; deploy/README.md, Backups).
  • If n8n stops, nothing is sent, but nothing else stops: bookings, bills and check-ins go on, and each message is tried again, up to three times (B5.2).
  • If Firebase sign-in stops answering, nobody can sign in. Connection health shows it red.

Left out, and why

  • A standby server: once five or more hotels pay D27-276 (1).
  • Online payments: guests pay at the desk for now D17-57 D25-36; planned for after the release of early October D27-239.
  • Our own booking engine: SU's booking engine is used instead D27-180.
  • Desktop and phone apps: the web version first; the apps later D21-98.
  • Electronic invoicing (IRN): required only above ₹5 crore turnover; the group is under it (deploy/README.md).
  • One merged system with the CRS and the leads app: they stay separate apps D27-276 (7).
