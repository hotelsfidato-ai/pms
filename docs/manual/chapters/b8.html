Chapter B8

Tests and checks

For the owner. What is checked before any change is called finished: each of the automatic checks (the "gates"), what each one proves and what it cannot prove, the latest counts, the habit of making a test fail before trusting it, and the check that keeps this book current.

B8.1Why there are gates at all

A change to the system is three kinds of risk at once: it may not do what was asked, it may break something it never touched, and it may work on this computer and fail on the server. Nobody can check all of that by eye, across every screen and a database built up by 211 migrations. So every change is run past the same set of automatic checks, called gates, and is finished only when all of them pass.

Three habits sit around the gates, and they come from your own rules (HANDOVER § 5, AGENTS.md):

  • Open the screen before saying it works. Most of the faults in the project's list of mistakes (MEMORY.md) were found by using the system, not by a gate.
  • Run the checks you quote. "2,546 tests pass" is only true if they were run on that exact code, in that session.
  • A guard is not a guard until it has refused something. A new test is trusted only after it has been seen to fail with the fault put back (B8.6).

Why it works this way

Since 19 September nothing leaves this machine (B9.2). Before that, the same checks also ran on a GitHub server on every push, and a push was not finished until that run was green (MEMORY 300). With no pushes, that second opinion is gone: a green run of scripts/gates.sh on this PC is the whole of the proof, so it is never skipped and never shortened before a merge or a release.

B8.2The full run: scripts/gates.sh

One command runs every gate, one after another, on the copy of the code it sits in:

  1. bash scripts/gates.sh <label> runs everything. This is the run that counts.
  2. bash scripts/gates.sh <label> quick runs only the type checks, the strip check and the website tests (about four minutes), for checking work in progress. It says on its last line that the rest were not run.

The full run has eight steps. The website build (B8.3) is run straight after it, by hand and again by the release script.

Why each step is there

  • strip: on 8 September one line of perfectly valid code took the live API down in a restart loop after three clean builds and every test had passed, because the live server loads code in a stricter way than any test did (MEMORY 209). The server's update script now runs the same check before it restarts anything.
  • api tests on a throw-away database: the tests once shared the database people were using. Clean-ups that did too little filled the demo with phantom guests; one that did too much deleted a real banquet booking somebody had just made (MEMORY 120). Each run now builds its own database and drops it.
  • database, as the application's login: a test run as the database's superuser passes every privacy rule, because a superuser ignores them. The isolation suite connects as the application does, so an open door shows.
  • replay: an early attempt to answer "can the migrations run twice?" was made on a real database, half-applied, and the database had to be rebuilt (MEMORY 119). Later, older migrations quietly undid newer ones on a second run (MEMORY 284, 293, 299). The replay runs on a scratch database holding a hotel, so it catches both.
  • pg16: the live server runs PostgreSQL 16.15 while this PC runs 17. A backup made on 17 could not be read by 16 (MEMORY 190); a migration using something only 17 knows would stop a live update half-way. Your yes, 4 October.

B8.3The build, and "no test sign-in in the build"

npm run build compiles the website into the files Firebase serves. Its last step reads every built file and fails the build if any trace of the test sign-ins is there: the Owner, General Manager and Reception buttons that sign in on this PC without a password, and the guest page's development-only code display. A good build ends with “✓ no test sign-in in dist (40 files checked)”.

There is a second lock on the server: the API refuses to start at all when the test sign-in is switched on and it is running as production.

npm run build:app, used for a release, does the same and writes the live API's address into the website's settings file. It refuses an address that is missing or not https.

Why it works this way

Your instruction of 14 September: keep the test sign-ins simple on this PC and remove them from production. A passwordless owner sign-in on the live page would let a stranger in as you; it happened once, on the live login page, before the check existed (MEMORY 193). A build that succeeds says nothing about what it contains, so the check reads the output itself.

Watch out

  • The build is not one of the eight steps of gates.sh. It is run beside it, and the release script (B9.3) builds again in the release copy and checks the result. Twice the gates were green and the website would not build (MEMORY 337, 378).

B8.5A run is judged by what it did, not what it printed

  • Each step is judged by its exit code, the yes-or-no a program hands back, never by its summary line (MEMORY 274). A summary can say "all tests passed" while a whole test file failed while tidying up (MEMORY 25, 361).
  • And by its last line. A check killed from outside on Windows reports "success" with its log cut short; one database step "passed" in 22 seconds that way (MEMORY 333). Each test step now names the line a passing run ends with (“all 1578 assertions passed”), and a run without it is marked “CUT SHORT” and failed.
  • The run records what it judged. The first line of its progress file names the exact commit, whether it was a full or quick run, and dirty if the copy had changes not yet committed. The release script refuses a release unless a full, clean, green run exists for exactly the release's commit (B9.3).
  • One run at a time. Several at once exhausted the machine on 18 September and a whole round produced nothing. The steps that build databases also wait their turn in a queue shared by every working copy on the machine (MEMORY 341): two copies building at once collided on the shared database logins.
  • A step that writes as it goes. Each step writes a line to .local\gates\progress.txt as it finishes, so a run in progress can be watched. You stopped a run on 18 September because twenty minutes passed with no sign of life.

B8.6"Fails first": making a test prove itself

A test that passes proves nothing until it has been seen to fail. So every new guard is proven the same way:

  1. Write the test, and see it pass on the fixed code.
  2. Put the fault back: change the code to what it was, or break the one line the test is about.
  3. Run the test. It must fail, and fail for the right reason.
  4. Put the code back exactly as it was, byte for byte, and see it pass again.

The changelog says, for every change, which guards were proven this way. For the work of 9 October: custom add-ons, 6 server guards and 5 screen guards; the KOT section, 7 server and 6 screen guards. One of them passed with its fault put back: "Print here" cleared the waiting bills in two places, so removing one proved nothing. The two were folded into one, and then the test failed as it should.

Why it works this way

Eleven guards in this project once passed with the very fault they were written for put back (MEMORY 166, 195): a test compared a number with itself, a test that inserted nothing could never find anything, a check that quietly skipped when its subject was missing. Each looked like protection and was not. A test that has failed on purpose at least once is known to be looking at the right thing.

B8.7The book's own check

Your rule of 9 October: a change to a screen updates its chapter in the same commit, and a test fails when the book falls behind (D27-293). src/test/manual.test.ts runs with the website tests and checks three things:

  1. Every menu screen of a written chapter's part is named in it. Each part of the menu that has its chapter is listed in the test; the restaurant's menu (Point of sale) is covered by A8 today. A new screen in that menu fails the test until A8 says what it is.
  2. manual.html is built from the chapters as they are. The book is one file per chapter; docs/manual/tools/build.mjs joins them. Nobody edits the joined book by hand.
  3. Every picture a chapter shows exists in docs/manual/img.

Each of the three was seen to fail before it was trusted (B8.6).

Watch out

  • When a chapter is added or changed, check 2 fails until the book is built again. When several people write at once, only the person merging runs the build (docs/manual/WRITING.md).
  • Part B chapters are not tied to a menu section, so check 1 does not cover them: keeping them true is a matter of writing, not of a test.
