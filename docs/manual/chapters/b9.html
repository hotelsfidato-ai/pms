B9.2The rule of 19 September: nothing leaves this machine

Your words of 19 September, which outrank every other working rule: “all the things are committed locally and nothing is pushed to actions, also [not] deploy the site”. In practice:

  • No push to GitHub: no branch, no shortcut around the checks, not even "just to run the check there".
  • No GitHub Action runs, because nothing reaches GitHub (the check described in B8.1 sits idle).
  • No deploy: not the API, not the website, not the deploy button.
  • Work is finished when it is committed on this machine with its gates run here. A green bash scripts/gates.sh <label> is the proof (B8).
  • Helpers working on one service commit in their own copy; the main chat merges them on this machine. They do not push either.
  • The book itself stays on this machine: it is not published anywhere (D27-293).

It lifts only when you say so, in your own words. The times it has been lifted are on the record: a push on the day of a release, for that push only, typed by you (D21-49, D21-50); and the backup push of 29 September, when drive D: of the old laptop was failing, which sent every branch to GitHub under a backup name so that no check ran (D27-155). On 4 October you confirmed the rule stands while releases go out whenever something is ready (D27-276).

Why it works this way

Live is yours to change. A release reaches guests and the hotel's money, and it is easier to keep a change from leaving than to bring it back. Holding everything on this machine means every release is a deliberate act: you decide it, you type it, and you see each step answer.

B9.3How a release is made

A release is a branch named for the day, such as release/all-5oct, cut from cp6 (the working line) when you ask for one.

On this PC, before you are asked to type anything

  1. Everything for the release is merged into cp6 and the full gates are green on that exact commit (B8.2).
  2. node scripts/release.mjs <branch> checks the release and refuses, with a sentence, unless: the push to GitHub would be a plain fast-forward; a full, clean, green gates run exists for exactly this commit; the release has its own copy of the code with nothing uncommitted; the website builds in that copy with the sign-in settings; and the built website holds the live API address, the sign-in settings and no test sign-in.
  3. Then it prints your steps, each labelled with where it runs. It never pushes, deploys or touches the server itself, and never prints a secret.

On the day: your steps (the shape every release follows)

  1. Your PC: push the release branch to GitHub (the one push the rule allows that day).
  2. The server: a backup before anything changes.
  3. The server: pull the new code.
  4. The server: deploy/launch.sh. It checks the server can load the code (the strip check) before restarting anything, applies the database changes as one transaction, restarts the API, and runs the readiness check. It ends in green, “https://api.fidatohotels.com is live.”, or stops with what is wrong.
  5. Your PC: ask the API's health address; it must answer with today's start time.
  6. Your PC: publish the website from the release copy (firebase deploy --only hosting:app).
  7. Look at it: open the site, reload, sign in, open the screens that changed. The master chat then looks at the live site and server read-only.
  8. The practice hotel first: before the staff are told, in AMRT: a booking for tonight, checked in, a payment and the bill; the night audit screen; what the release changed; Connection health with no row newly red. All right: tell the staff. Anything wrong: stop and tell the master chat D27-373 (A5). One server runs every hotel, so this is a check before people use it, not a separate practice server.
  • Server first, then the website: new screens need the new server.
  • At a quiet moment, never during a night audit. The API restarts for a few seconds; the offline queue on each device holds anything tapped meanwhile.
  • Screens already open elsewhere say “A new version is ready”: reload between guests.

Why it works this way

You type every command and the master guides and reads each output (D21-50). The backup comes first because a database change cannot be undone, while the website can be rolled back at once (docs/GO-LIVE-PLAN.md). The release script exists because two releases went wrong in ways no gate could see (B9.4); since your decision of 4 October it checks itself rather than relying on anyone's memory (D27-276, D27-277).

B9.6Backups, and getting one back

Every night

At 03:00, after any likely night audit and before anyone arrives, the server:

  1. Takes a backup of the database, in a form that can give back one table on its own. It keeps the last 14 on its own disk.
  2. Copies it to a storage bucket off the server, when the bucket's upload link is set.
  3. Restores it into a scratch database and compares it with the live one, table by table and the money to the paisa. A backup is called sound only if restoring it gives back what was there.
  4. Writes one status line to its log, which System health and Connection health read, and tells you, pass or fail, through n8n when the alert link is set.

Each customer's database, when there are customers, is backed up at 03:30, one after another, each with its own log.

At 03:15 the files uploaded into the PMS (bill photos, petty-cash receipts, repair and bar bills) that are not yet in the bucket are copied to it, in a folder uploads, once their own upload link is set. Each night sends only the new ones, and they never expire from the bucket: the rule that deletes the database's copies after 31 days leaves that folder out, because a bill must be produced years later D27-377. Guests' ID photos are not among them: they were never on the server (B5).

At 03:30 n8n's own backup saves its workflows and its saved logins (still locked) and copies them to the same bucket, in a folder n8n, when n8n's copy of the upload link is set. The key that unlocks those logins never leaves the server D27-373 (A1). Since D27-377 it writes its result where Connection health reads it, so a failed night turns the Backups row red.

Watch out: today the backups do not leave the server

  • You chose an Oracle bucket in Fidato's own account, 30 days kept there, and a WhatsApp through n8n when a backup fails (D27-18, D27-19, D27-20). The read-only check of 4 October found the upload link and the alert link both empty: every backup was on the same disk as the database it protects (MEMORY 385). On 5 October the bucket was put on hold (D27-285). Until it is set up, losing the server loses the backups with it.
  • The steps to set it up are in deploy/README.md, "Backups", steps 1, 3 and 4: the bucket with a 30-day lock, an upload-only link, the server's settings file, then one run on purpose and one deliberate failure to see the alert arrive.
  • Your decision of 4 October also asks for a full restore rehearsed every month, and a standby server once five or more hotels pay (D27-276). No rehearsal is recorded yet.

Getting a copy back

  • To check a backup without touching anything: db/verify-backup.sh <file> restores it into a scratch database, compares it, and drops the scratch database.
  • To put a backup back: db/restore.sh <file> or db/restore.sh --latest. It says what it is about to overwrite, waits for the database's name to be typed, and first takes a safety backup of what it replaces. There is no undo; that is why it asks. A backup does not carry the application's database rights, so they are put back before the API uses the restored database: deploy/README.md does it by running deploy/launch.sh again, which applies the migrations.
  • From the bucket (once it exists): the Oracle console, the bucket, Objects, the file, Download.
  • An uploaded file (a bill photo or a receipt gone from the server, or all of them on a new server): a read link made in the Oracle console on the day, then one command on the server fetches every file the database names that the server lacks, and names any the bucket does not have (deploy/README.md, "Getting a copy back"). A file uploaded since the last 03:15 copy is not in the bucket.
  • From this PC's version of PostgreSQL (17) to the server's (16): only with db/backup.sh --portable. A normal backup made on 17 cannot be read by 16 (MEMORY 190).

Getting back any minute of the last month

Once it is switched on (deploy/README.md, "Restore to any minute"), the database's change journal goes to the same bucket at least once an hour, and a base copy every Sunday, so the database can be brought back to any minute of the last 31 days, not only to last night D27-373 (A3).

  • It never goes over the live database. The chosen minute is rebuilt in a temporary copy and handed over as a separate database, fidato_pitr, beside the live one. You compare the two, then decide: take back only what was lost, switch the whole database to that minute (everything after it is lost, at every hotel), or drop it.
  • At most about an hour of changes is not yet off the server at any moment.
  • Connection health's Backups row turns red when the journal or the weekly base copy is not reaching the bucket.
  • Reading it back needs a read link you make in the Oracle console on the day, expiring the next day; the server never holds one.

If the server itself is lost

deploy/IF-THE-SERVER-DIES.md: a new server, from nothing to working, in under two hours, each step labelled with where it runs D27-373 (A6). It lists what to keep off the server beforehand (the SSH key, your logins, the settings you typed in), and what comes back from where: the files uploaded into the PMS come back from the bucket as of the last night's copy. The two hours are an estimate until you have rehearsed it once on a spare server, which is yours to do.

Why it works this way

A backup that has never been restored is not a backup: the classic disaster is a nightly job that ran for years and produced an empty or wrong file. So the nightly job restores what it took and compares it. It used to compare against fixed demo figures, and once printed "would not give you your hotel back" over a perfectly sound backup; it now compares with the source, so it never needs editing when the data changes (MEMORY 30, 34, 151).

B9.9When something breaks

The system is down, or slow

  • At the desk and in the restaurant: carry on. Each device holds what can safely be held and sends it when the line is back; what cannot be held is refused with a sentence saying what to do instead, usually “Take it on paper and enter it when the connection is back.” (A0.8).
  • Tell the master chat what you see. The first look at the server is read-only (D21-51); any write on live waits for your yes.

A release went wrong

  • The website is wrong: Firebase console, Hosting, Release history, the previous release, Roll back. Instant.
  • The server's update stopped with a red ✗: stop there and send the output. The database changes are one transaction, so a failure leaves the database exactly as it was, and when the new code cannot load, nothing is restarted: the old API keeps running.
  • Do not roll the server's code back on your own. Stop and send the output; the master names the commit that is safe to return to, if there is one, because an older version can reopen a security hole a newer one closed (HANDOVER § 9). Database changes cannot be undone: for the data, the backup taken before the update is the way back (B9.6).
  • The update finished but says "NOT READY TO SERVE": the readiness check names what is wrong (a test sign-in switched on, a staff member with no sign-in, a placeholder that would print on invoices, a hotel with no rooms). Fix that, and run the check again.

Someone may have broken in, or guests' data may have leaked

docs/INCIDENT-PLAN.md is the plan, written from the CERT-In Directions. In short:

  1. Write down the time you noticed or were told. CERT-In must have a first report within 6 hours of that moment; a partial report is fine. Not reporting can cost up to ₹1 crore. When in doubt, report.
  2. Hour 0 to 1: stop it spreading and keep the evidence. Do not wipe or "clean up" the server: its logs are the evidence. If someone is inside now, stop the server in the Oracle console (the hotels work from paper meanwhile) and copy its disk first. Disable a misused staff account in Firebase. Change any leaked key or password.
  3. Hour 1 to 5: report to CERT-In by email or phone (the contacts are in the plan): who is reporting, what happened, when it happened and when it was noticed, which system, what has been done.
  4. After: send the rest as it is learned, save the logs, tell the hotels affected, and write down what happened and what changed.

You are the Point of Contact for both Fidato Hotels and Influvate (D27-22). Filing the two Point of Contact forms is the first thing to do: until then CERT-In has no name for either company. The forms are at the end of the plan.

Watch out

  • Staff sign-in logs sit with Google (Firebase), not on the server. Whether that satisfies CERT-In is a question for the lawyer, listed in the plan as still open.
  • From 13 May 2027 a data breach must also be told to the guests affected and to the Data Protection Board (the DPDP Rules). The plan notes it as not yet in force.
