## Findings in detail

### S-1 The bell's query does per-booking work for every booking ever: 1-2 s quiet, 6-26 s under load
- Telemetry: GET /notifications avg 6,775 ms / 6,311 / 6,180 in fidato / s28 / s30; worst 11,350 /
  26,594 / 26,471 ms. Its query appears in the slow-query log 43 times in `fidato` (max 11,280 ms).
- Measured on fidato_s34: execution 1,000-1,165 ms (3 runs), first run 2,328 ms. In the browser, the
  bell answered 4.9 s after sign-in (queued behind the Dashboard's other requests).
- Cause (plan): the CTE `balances` is used three times, so it is materialised for all 778 bookings, and
  for each one it calls `app.stay_room(r.id)`: 778 x ~1.3 ms = 1,000 ms (timed alone), because each
  call runs its own query under RLS (`hotel_id in (select app.auth_hotel_ids())` on room_assignments
  and rooms). The correlated balance sum is only 44 ms (0.056 ms x 778; indexes are used).
- Sized fix (scratch query, not code): call `app.stay_room` only for the rows returned (final select)
  instead of inside `balances`: 100-127 ms, the same 6 rows, identical checksum. ~10x.
- File: `api/src/routes/notifications.ts` (core). Round F (`fix/leftovers-28sep`) also edits it
  (D27-153); its heavy query is unchanged there.

### S-2 Slow requests exhaust the 10-connection pool; the rest fail after exactly 5 s
- `api/src/db.ts`: pool max 10, `connectionTimeoutMillis` 5,000.
- Every 500 in the telemetry took 5,011-5,025 ms: fidato_s28 10 (on /hotels, /stays, /rooms, /house-now,
  /notifications, /reports/manager), fidato_s30 3 (/hotels, /modules, /notifications), all in the first
  minute of a session (the Dashboard's burst). QA X-7 saw the same ("connection timeout").
- This is the likeliest cause of "some workflows work, some don't": a screen whose read is refused by
  the pool shows an error, and a second try works.

### S-3 /stays sends every booking ever (442 KB), and Dashboard and Rooms ask for it three times each
- Owner sign-in to Dashboard (dev): 14 requests, network quiet after 5.5 s; /stays x3 at 442 KB each
  (1.3 MB of JSON), finished at 1.1 / 1.9 / 2.7 s (queued); manager report 2.8 s; bell 4.9 s.
- Rooms from the menu: /stays x3 again, 1.3 MB, quiet after 2.6 s.
- SQL alone: 112 ms planning + 176 ms execution (plan: half the execution is `app.is_active_staff()`
  per guest row from guests' RLS). The rest is building and sending 442 KB, three times.
- Code: `DashboardPage` builds `getStayView` (rooms, stays, folios, house-now), `fetchStays` again, and
  `EveryHotel` a second `getStayView` through `getStayViewCounts`; each is its own query key.
- Telemetry: GET /stays avg 1,320 / 2,346 / 1,285 ms, worst 8,615 / 24,138 / 10,146 ms.

### S-4 In house asks for each guest's bill separately (N+1 from the browser)
